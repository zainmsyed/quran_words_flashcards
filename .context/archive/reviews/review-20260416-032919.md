### Finding 3 — Reactivity gap: manifest updates are not surfaced by Svelte reactivity (potential subtle UI inconsistency)
- Severity: medium
- Category: bug/regression
- Summary: the UI depends on a non-reactive global Set (bundledAudioIds) in src/core/tts-adapter.ts. Card.svelte awaits loadBundledAudioManifest() in onMount to recompute availability, which covers the common mounting scenarios, but components that remain mounted and rely on reactive updates could miss manifest-driven changes because Svelte reactivity does not automatically track changes to an ordinary Set.
- Evidence:
  - src/core/tts-adapter.ts maintains bundledAudioIds as a JS Set and exposes hasBundledAudioForWordId(wordId) which returns bundledAudioIds.has(wordId).
  - src/ui/components/Card.svelte uses a Svelte reactive statement ($: ttsAvailable = canPronounceWord(word?.id || '')) but Svelte will only re-evaluate that when referenced *reactive* dependencies change (e.g., word). Changes to the non-reactive bundledAudioIds Set will not trigger re-evaluation unless the component explicitly re-checks, which is currently done only on mount.
- Recommendation:
  - Expose audio availability via a Svelte store (Writable/Readable) or an EventEmitter subscription so components can subscribe and update automatically when the manifest changes. For example, export a readable store `bundledAudioIdsStore` from tts-adapter and update it when the manifest loads. In components, subscribe or use $bundledAudioIdsStore in a derived reactive statement.
  - Alternatively, emit a small custom event on `window` or provide a subscribe() API in tts-adapter that calls listeners when the set changes; ensure Card.svelte registers a listener and invalidates/recomputes ttsAvailable.
- Rule candidate: Prefer Svelte stores or explicit subscription APIs for cross-component runtime state changes so UI reactivity is reliable (yes)

### Finding 4 — Hard-coded DEFAULT_BUNDLED_IDS duplicates seed data
- Severity: low
- Category: simplification
- Summary: the tts-adapter uses a small hard-coded default set of bundled IDs (w1..w10) while manifest loads. This duplicates knowledge of the seed deck in two places and risks desynchronization.
- Evidence:
  - src/core/tts-adapter.ts contains DEFAULT_BUNDLED_IDS = ['w1',...'w10'] which is used to pre-populate the bundledAudioIds set during manifest fetch.
- Recommendation:
  - Derive the default set from src/data/seed-words.json (e.g., read the file at build time or import the seed list) or keep the default set empty and adjust UX (show a loading state or conservative disabled audio control) until the manifest is available.
  - If a small default is desired for UX, generate it programmatically from the canonical seed list (avoid duplication).
- Rule candidate: —

### Finding 5 — Generator code: minor deprecation & consistency notes
- Severity: low
- Category: simplification
- Summary: scripts/generate_audio_gcp.py uses datetime.utcnow() (deprecated warning) and the gTTS prototype script does not emit a manifest in the same format as the GCP generator, which creates a minor inconsistency in tooling.
- Evidence:
  - scripts/generate_audio_gcp.py prints a DeprecationWarning for datetime.datetime.utcnow() when invoked in this environment.
  - scripts/generate_audio_gtts.py (POC) generates files but does not write manifest.json; the manifest was produced by running the GCP generator in manifest-only mode after the gTTS run.
- Recommendation:
  - Switch to timezone-aware timestamps in generate_audio_gcp.py, e.g. datetime.now(datetime.UTC) or use datetime.now(timezone.utc) to avoid deprecation warnings.
  - Consider adding optional manifest writing to the gTTS prototype so both generators produce consistent manifest output and tooling is interchangeable for QA.
- Rule candidate: —
