## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: A newly generated study queue is never persisted until the first rating, so refreshing or reopening the app before answering a card can reshuffle the session and lose same-day resume state.
- Evidence: `StudySession.svelte` builds a session in memory on startup (`initializeSession()` calls `buildSession(effectiveSession || undefined)` at `src/ui/StudySession.svelte:87-115`) and when starting a fresh session (`startFreshSession()` at `src/ui/StudySession.svelte:203-214`) but never saves the generated queue. The only persistence paths are `persistStudySnapshot()` after ratings (`handleRate()` at `src/ui/StudySession.svelte:139-180`) and `reviewCompletedSession()`. Because `buildSessionPlan()` randomizes card order/mode via `Math.random`, a reload before the first answer can produce a different queue than the one the user just started.
- Recommendation: Persist the generated queue immediately after building a fresh session, including the "start fresh" path, so the same-day session survives refresh/reopen even before the first rating.
- Rule candidate: Persist a newly generated session queue before the user can refresh or switch devices if same-day resume depends on it.

### Finding 2
- Severity: medium
- Category: bug
- Summary: Card progress and session/stats state are written in separate PocketBase requests, so a mid-save failure can leave the server in a partially updated state that the client cannot recover from cleanly.
- Evidence: `handleRate()` first awaits `savePocketBaseCardState(authSession!, updated)` and then `persistStudySnapshot(nextStats, nextSession)` (`src/ui/StudySession.svelte:161-175`). If the second write fails, the card progress record has already advanced on the server while `study_state` remains stale; the client also does not advance its local state because the local updates happen only after both awaits complete. The same split-write pattern exists in `startFreshSession()` (`src/ui/StudySession.svelte:203-214`), which clears `study_state` and rebuilds a queue without persisting the new queue afterward.
- Recommendation: Store the coupled session/stats state in one atomic write path or add a deterministic recovery step that reloads from PocketBase and reconciles the client when one of the two writes fails.
- Rule candidate: Do not split coupled user-visible state across multiple writes unless you also have a transaction or a guaranteed recovery path.

### Finding 3
- Severity: low
- Category: test-gap
- Summary: The new `study_state` persistence path is not exercised end-to-end by automated smoke tests, so regressions in session/stats round-tripping could slip through.
- Evidence: `scripts/pocketbase-smoke-test.mjs` checks that `study_state` exists (`lines 147-154`), but the actual CRUD and permission assertions only cover `card_progress` (`lines 183-236`). There is no smoke coverage for creating/updating/fetching `study_state`, no cross-user denial check for that collection, and no round-trip test for `savePocketBaseStudyState()` / `loadAuthenticatedStudySnapshot()`.
- Recommendation: Add a smoke test that writes and reads a `study_state` record for one user, confirms another user cannot access it, and verifies a saved session/stat blob survives a load/save round-trip.
- Rule candidate: Add smoke coverage for every persisted collection and every user-visible read/write path.
