## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: `buildSessionPlan()` still hard-caps reviews at 5, so sessions with fewer than 10 new cards stop well short of the 15-card cap instead of filling the remaining slots with due reviews.
- Evidence:
  - `.context/stories/story-016.md:45` says sessions should "fill remaining slots with the oldest due reviews first" when fewer than 10 new words are available.
  - `src/core/session.ts:141-154` sets `targetReview = Math.min(maxReview, dueAll.length, (maxNew + maxReview) - targetNew)`, so review selection can never exceed `reviewPerSession` (5).
  - Manual repro on the current code with 6 new cards and 20 due reviews returned `{ queueLength: 11, newCount: 6, reviewCount: 5 }`, leaving 4 slots unused.
- Recommendation: Derive review slots from the remaining session capacity when due reviews exist (up to 15 total), then add quota tests for 0, 1-4, 5-9, and 10+ new-card mixes.
- Rule candidate: When a quota says to fill the remaining slots, compute the secondary quota from remaining capacity instead of applying a fixed sub-cap unconditionally.

### Finding 2
- Severity: medium
- Category: regression
- Summary: The Stats screen now uses a different "due" predicate than the planner/summary, so mastered overdue words can still appear in the “Due today” list even though the due count and review queue exclude them.
- Evidence:
  - `src/core/progress-summary.ts:33-40` excludes `easyCount >= MASTERED_EASY_COUNT` from `dueCount`.
  - `src/ui/Stats.svelte:17-19` still computes `due` as only `interval > 0 && dueDate <= now`, and `src/ui/Stats.svelte:32-36` builds the due filter with `entries.filter((e) => e.due)`.
  - Result: the stat tile count comes from `summary.dueCount`, but clicking it can show extra mastered cards and mismatched totals.
- Recommendation: Reuse the same due/mastery predicate in `Stats.svelte` that `progress-summary.ts` and `session.ts` use, ideally via a shared helper, and add a regression test for a mastered-overdue card.
- Rule candidate: When a count and a filtered list represent the same state, derive both from the same shared predicate so they cannot drift.

### Finding 3
- Severity: medium
- Category: regression
- Summary: The mastered overlay’s “Start new session” button no longer performs a meaningful action once every card is mastered.
- Evidence:
  - `src/ui/StudySession.svelte:246-251` rebuilds the session with `buildSession(undefined)`.
  - `src/core/session.ts:126-157` now excludes mastered cards from `dueAll`; a manual repro with an all-mastered deck returned `{ queueLength: 0, newCount: 0, reviewCount: 0 }`.
  - `src/ui/StudySession.svelte:50`, `316`, and `390-406` keep the overlay visible whenever `allMastered && currentIndex >= deck.length`, so rebuilding an empty queue leaves the user on the same overlay with the same CTA.
- Recommendation: Replace or redefine the CTA so it performs a real action for an all-mastered deck (for example reset progress, open mastered-word review, or route to a non-overlay empty state), and add a regression test around that path.
- Rule candidate: —

### Finding 5
- Severity: low
- Category: bug
- Summary: A failed bundled-audio manifest load is cached permanently, so non-speech environments can get stuck with only the default 10 audio-enabled words until the page reloads.
- Evidence:
  - `src/core/tts-adapter.ts:42-67` memoizes the first `manifestLoadPromise` and never clears it when `fetch()` fails or returns `!ok`.
  - Manual repro on the current module with a first `503` response and a second successful manifest response made only one fetch call; `hasBundledAudioForWordId('w200')` stayed `false` on the second call.
  - `scripts/run-tests.mjs:299-341` only tests the successful manifest path; there is no failed-then-successful retry coverage.
- Recommendation: Clear `manifestLoadPromise` when manifest loading fails/non-OK (or add an explicit force-reload path) and add a regression test for failed-then-successful manifest loading.
- Rule candidate: When optional runtime manifests fail to load, do not cache the failure permanently; allow later retries.
