## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: Study mode is never randomized; every session item is forced to `ar2en`, so the English→Arabic branch in `Card.svelte` is unreachable.
- Evidence: `StudySession.svelte` declares `SessionItem.mode` as `'ar2en' | 'en2ar'`, but both session builders assign `mode: 'ar2en'` (`buildSession()` lines 78–82 and 108–110) and the hard requeue path does the same (`handleRate()` lines 175–177). `Card.svelte` has a separate `en2ar` branch (`lines 97–136`), but the app never emits that mode.
- Recommendation: Either randomize per card/session or remove the `mode` union and dead branch until bidirectional study is actually implemented. Add a regression test for both directions.
- Rule candidate: Don't persist a mode enum if every producer hardcodes the same value.

### Finding 2
- Severity: medium
- Category: bug
- Summary: The stats screen treats "studied" as unique reviewed words, not total study volume, so repeated reviews are collapsed and the dashboard cannot compute the intended easy-rate metric.
- Evidence: `StudySession.svelte` rewrites `appStats.studied` on mount to `Object.values(states).filter((s) => (s?.reviewCount ?? 0) > 0).length` (`lines 126–131`), and `handleRate()` only calls `recordStudy(..., isNew)` with `isNew = prev.interval === 0` (`lines 166–171`). `Stats.svelte` then displays `studiedCount = studiedEntries.length` (`lines 20–23`) rather than any total-review counter. `AppStats` only tracks `studied`, `easy`, and `streak` (`src/core/app-stats.ts:1–50`), so there is no denominator for an easy-rate percentage.
- Recommendation: Split unique-word progress from total review counts, keep the intended total-study metric in storage, and add an explicit easy-rate calculation to the dashboard.
- Rule candidate: Keep unique-item counters separate from total-event counters when a dashboard needs both.

### Finding 3
- Severity: medium
- Category: bug
- Summary: The deck schema and card UI do not carry Quranic verse context, so cards cannot show the required example verse or surah:ayah reference.
- Evidence: `Word` only exposes `id`, `arabic`, `transliteration`, and `english` in `src/core/wordlist.ts:1–67`, and `Card.svelte` renders only those three fields (`lines 74–136`). A repo search finds no app code handling `verse`, `surah`, or `ayah`, so the intake PRD’s "every card shows an authentic Quranic verse" requirement is unmet in the current data model.
- Recommendation: Extend the seed schema and `Word` type with verse text and reference fields, then render them on the card back; if that work is intentionally deferred, record it explicitly in the story backlog.
- Rule candidate: —

### Finding 4
- Severity: low
- Category: test-gap
- Summary: The repo has no automated tests for the fragile SRS/session/storage logic, so regressions in rating math or localStorage keys can slip through.
- Evidence: `package.json` only defines `dev`, `build`, and `preview` scripts (`lines 6–18`), and there are no `*.test.*`/`*.spec.*` files or `tests/` directory in the repo. The highest-risk code paths are `src/core/srs.ts`, `src/core/app-stats.ts`, and `src/ui/StudySession.svelte`, which drive persistence and scheduling.
- Recommendation: Add Vitest coverage for SRS transitions, streak rollover, and session resume/save behavior before changing storage formats or session rules again.
- Rule candidate: Add automated coverage before changing persistence formats or session state machines.
