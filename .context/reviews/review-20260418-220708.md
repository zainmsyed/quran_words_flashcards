## Findings
### Finding 1
- Severity: medium
- Category: bug
- Summary: A failed `study_state` save can leave the next reload using stale session metadata, because the app retries by reloading `study_state` even after `card_progress` was already advanced.
- Evidence:
  - `src/ui/StudySession.svelte:126-166, 198-246, 268-300` writes `card_progress` first, then persists `study_state`; if the second write fails, the catch path calls `retryLoad()` instead of reconciling the partially saved state.
  - `src/core/pocketbase-study.ts:311-320` prefers the persisted `study_state` snapshot whenever one exists, even if `card_progress` has already been updated and the auxiliary snapshot is now stale.
  - That means a recoverable network/write failure can come back with updated card progress but stale app stats or session queue, which is exactly the kind of inconsistent session state this story is trying to harden.
- Recommendation: Make the paired PocketBase writes atomic, or change recovery to reconstruct the session/app stats from `card_progress` when the auxiliary `study_state` write fails.
- Rule candidate: When multiple records represent one logical snapshot, recover from the durable source of truth instead of trusting a stale auxiliary snapshot.

### Finding 2
- Severity: medium
- Category: test-gap
- Summary: The new `sessionissue` / sign-out flow is only covered by helper tests and the PocketBase smoke harness, so a regression in the App → Settings/StudySession/AccountSettings event chain could leave stale session UI or audio state untested.
- Evidence:
  - `src/App.svelte:158-169` wires `on:sessionissue` from `StudySession` and `Settings` into the top-level auth/session state machine.
  - `src/ui/Settings.svelte:30-115`, `src/ui/AccountSettings.svelte:11-36`, and `src/ui/StudySession.svelte:34-96` implement the custom session-issue dispatch chain.
  - `scripts/run-tests.mjs:85-770` covers core helpers, storage, auth parsing, TTS, and the PocketBase smoke helper, but it does not mount the Svelte components or assert the security-sensitive UI transitions.
- Recommendation: Add a minimal component or Playwright-style test that forces unauthorized/unavailable session issues and asserts the app switches to login/unavailable while clearing sensitive state and stopping audio.
- Rule candidate: When a security-sensitive UI flow depends on custom component events, add component/e2e coverage for the dispatch chain instead of only testing helper modules.
